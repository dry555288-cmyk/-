## 1. 项目简介

MineSim-Dynamic 是面向露天矿非结构化道路自动驾驶矿卡的场景化闭环规划仿真项目。本项目不是单纯“实现一个 MCTS”，而是在原始 MineSim 工程上逐步完成以下主线：

**MineSim 原项目复现 → Pure MCTS 接入 → 单车闭环 → 多车 / Fleet MCTS → 双车冲突 benchmark → 真实 GeoJSON 新地图 → Full-Mine Vector V2 → 全矿 targeted runtime 验收。**

当前项目已经越过早期“能否复现”“MCTS 能否接进去”“单车能否跑通”的阶段。Pure MCTS、Multi/Fleet MCTS、J117 双车 benchmark、Full-Mine Semantic 和基础运行链都已有实际闭环证据；目前工程重点是把 **Vector V2 新地图的 7 个 targeted 场景全部正式跑通并冻结版本**。

项目研究问题主要包括：

* 多步 MCTS 是否能比传统反应式 IDM 在复杂冲突中获得更好的安全与任务完成能力；
* 两辆受控矿卡能否通过联合搜索自主形成时序分离，而不是依赖固定优先级；
* 如何建立公平、可解释的多规划器 benchmark；
* 如何把真实矿区 GIS / GeoJSON 数据转换成 MineSim 可加载、可搜索、可闭环运行的地图；
* 如何让全部实验具备版本、配置、日志、随机种子和结果可追溯性。

export PYTHONPATH=/root/MineSim-Dynamic

git branch --show-current

其中：

* 正式仓库只有 `/root/MineSim-Dynamic`；

# 5. MineSim 闭环架构

当前项目真实闭环可概括为：

**Scenario / Map → Planner → Trajectory → Controller → Vehicle Model → Observation → Metrics / History → 下一帧**

更具体地：

`ScenarioFileBaseInfo / MineSimDynamicScenario`
→ `get_maps_api / MineSimMap`
→ `Planner.initialize()`
→ 每帧 `compute_trajectory()`
→ `TwoStageController`
→ `iLQR / LQR tracker`
→ `Kinematic Bicycle Model`
→ 更新 EgoState
→ 更新其他 actor / observation
→ collision / boundary / goal / metrics
→ 下一 iteration。

需要特别注意：**Planner 输出的是未来轨迹，而不是下一帧车辆位置。** Controller 根据当前车辆状态和规划轨迹计算控制量，车辆模型再积分得到实际下一状态。因此搜索层、轨迹层、控制层和车辆动力学层必须分开诊断。

# 6. IDM Baseline

IDMPlanner 是当前工程的重要对照、回归基座和部分 MCTS 接口基础。

其基本流程是：

当前 EgoState
→ Global Route
→ surrounding-object occupancy map
→ 扩展自车前方 route corridor
→ 找到最近 leading object
→ IDMPolicy 根据距离、相对速度、headway 等计算纵向加速度
→ 沿 route 生成未来状态
→ `InterpolatedTrajectory`
→ Controller / KBM。

历史公共参数大致为：

* `target_velocity = 10.0 m/s`
* `min_gap = 1.0 m`
* `headway = 1.5 s`
* `accel_max = 1.0 m/s²`
* `decel_max = 3.0 m/s²`
* 16 个轨迹点
* 0.5 s 采样间隔

当前 targeted runtime 中，IDMPlanner initialize 后实际目标速度会调整到约 `10.5 m/s`。

# 7. Pure MCTS

Pure MCTS 没有重写整个 MineSim 执行栈，而是在既有 Planner / route / trajectory 接口之上，将反应式纵向决策替换为多步树搜索。

当前核心动作空间：

| Action |       加速度 |
| ------ | --------: |
| BRAKE  | -3.0 m/s² |
| DECEL  | -1.5 m/s² |
| KEEP   |         0 |
| ACCEL  | +1.0 m/s² |

历史正式核心参数：

* Search Budget：300
* `max_depth = 8`
* `tree_dt = 0.5 s`
* `c_uct = 1.4`
* `gamma = 0.99`
* 障碍预测：CV / CTRV
* 物理碰撞 buffer：约 0.5 m
* 连续净距安全阈值：约 3.0 m

每帧执行：

Selection → Expansion → Rollout → Backup → 根节点动作选择。

只执行搜索得到的第一步动作，下一仿真帧根据最新观测重新规划，因此属于 **receding-horizon MCTS**。

已经形成 448 条 strict MCTS expert samples，动作分布大致为：

`ACCEL 322 / KEEP 51 / DECEL 41 / BRAKE 34`

这些数据足以证明数据管线和训练 schema 的可行性，但样本来自连续时间序列且只有少数场景，不能直接随机逐行拆成 train / val，也不能据此宣称 Neural-MCTS 已完成。当前没有正式 Value Network、Policy Network、Policy-Value 或 PUCT 训练结果。

# 8. Multi / Fleet MCTS

多车阶段将两个受控车辆共同放入联合状态：

`controlled A + controlled B + external actors`
→ `FleetState`
→ 16 个联合动作
→ `FleetTransitionModel`
→ `FleetRewardModel`
→ best joint action
→ 两车 Controller / vehicle model 闭环执行。

FleetRewardModel 同时包含：

* per-vehicle progress / safety / efficiency；
* A-B 内部真实车辆几何；
* internal clearance soft penalty；
* hard collision / safety penalty；
* 外部 actor 的 CV / CTRV 几何预测。

Dapai A-B-only 实验已经形成了明确的联合时序机制证据：B 先通过，A 后通过；但加入外部 `object1` 后目标交互会被提前打断，因此 `object1` 被认定为 benchmark confounder。正确做法不是不断调整 reward 逼 full-external 场景成功，而是重新设计更干净的 benchmark。

Jiangtong V22 中，Traj26 虽然存在真实空间交点，但 actor 到达时间与 ego 最早可达 ETA 相差约 `+9.496 s`，并非天然近同时冲突，因此已经作为**负筛选结果**封存，不能通过修改 StartTime、速度、route、reward、budget 或 seed 人为把它包装成天然冲突。

# 10. Search Budget 消融

Pure MCTS 已进行 Budget：

`50 / 100 / 200 / 300`

的对照。

主要现象：

* Dapai 对搜索预算明显敏感，历史固定时限下只有 Budget 300 成功进入目标；
* Jiangtong 在较低预算下已经接近饱和；
* 固定对所有状态使用高 Budget 存在明显计算冗余。

因此后续合理研究方向包括：

**adaptive budget、tree reuse、value guidance / Value Network。**

但这些不应抢在当前新地图 runtime 7/7 验收之前。

# 11. J117：真实地图 Constructed Benchmark

为了摆脱 Dapai 外部 actor 混杂和 Jiangtong 缺少天然时间冲突的问题，项目从真实 Full-Mine GeoJSON 中选择 **Junction 117（J117）** 作为 pilot。

J117 的意义不是“随便造一个新地图”，而是首先证明完整链路：

**真实 GeoJSON → Raster/Semantic → MineSim Map API → Scenario → Planner → Controller → Runtime → Multi-Ego MCTS**

真实路线：

Route A：

`6670 → 6674 → 5690`

Route B：

`5691 → 6546 → 6523`

J117 Phase 4C 单车闭环结果：

* 423 steps
* 42.3 s
* 距离约 398.998 m
* min clearance ≈ 1.599 m
* goal reached
* 全程 drivable
* 无异常

随后 Phase 5 已完成双受控车辆与 Pure MCTS：

* NO-MCTS aligned baseline：crossing gap ≈ `0.00070 s`，minimum clearance = 0，发生真实几何冲突；
* Pure MCTS seed 0：crossing gap ≈ `1.561 s`；
* swept minimum clearance ≈ `0.594 m`；
* 5-seed robustness：`5/5 PASS`；
* 5-seed swept safety：`5/5 PASS`。

因此 J117 已经是一个冻结的 real-map constructed benchmark / 回归区域。除非生产源码发生可能影响 Map API、Planner、Controller 或车辆几何的修改，否则不需要重新调 J117 MCTS。

* node：400,744
* polygon：177
* road：93
* intersection：35
* loading_area：36

* dubins_pose：565
* reference_path：540

主要解决过三个系统级问题：

**共享 topology endpoint 不完全一致。**
同一 topo ID 建立 deterministic canonical XY，只 snap path 首尾。

**source coverage validator 漏 layer。**
明确建立 road / junction / loading / unloading / auxiliary 的 source→semantic mapping。

**boundary parent 错挂。**
不再跨类别只按 object ID 搜索，而是以 `rgn_type + rgn_objectid` 联合判断。

Full-Mine V1 同时发现，官方 MineSim 并未公开“原始 GIS → production bitmap”的制作工具，而官方 Dapai / Jiangtong 成品地图中 polygon 内也存在大量 non-drivable 区域，因此不能简单使用：

`whole polygon = drivable`

V1 最终采用：

**3.5 m lane-centered half-width + parent polygon clipping + 10 px/m**

生成明确标记为：

`DEV_ONLY_NOT_PRODUCTION_VALIDATED`

的可行驶 mask。

# 15. 高程与 Topology 政策

Vector V2 已将 `lane.geojson` 的 raw Z 写入：

`reference_path waypoint[3]`

但：

* elevation datum 尚未权威确认；
* `waypoint[4] slope` 当前仍为 `0.0`；
* boundary Z 存在明显异常，暂不作为 elevation truth；
* lane6713 存在约 `+0.519 m` 单步 seam，当前策略是**保留 raw Z + QA 标记**，不凭空平滑；
* 不同 topo ID 即使 XY 相同也不能自动 merge；
* 约 50 条 `gear=-1` lane 的实际运营方向仍没有权威业务解释。

因此：

**Topo ID 是首要拓扑事实，距离相近不能代替 topology identity。**

# 17. CollisionLookup 修复

C / D / E targeted runtime 曾暴露出两个不同问题：

第一类是真实 bitmap interface gap。

第二类是 MineSim `CollisionLookup` 自身车辆几何与标准 CarFootprint 不一致。

标准 XG90G：

* reference point：rear axle
* vehicle length：9 m
* width：4 m
* rear axle → head：+6.5 m
* rear axle → rear：-2.5 m
* rear axle → geometric center：+2 m

旧 CollisionLookup 中：

* `collision_lrear = 6.5`
* `collision_lhead = 2.5`

前后悬语义反置，同时一个角点使用 `-lrear/2`，使 lookup polygon 甚至不是标准矩形。

修复包括：

* `lrear: 6.5 → 2.5`
* `lhead: 2.5 → 6.5`
* 修复矩形 p1 角点
* lookup 黑像素命中后增加真实 XG90G footprint 与 0.1 m pixel 的精确 SAT 相交复核，用来过滤离散 lookup 的侧向假阳性，同时保留真实碰撞

最终 `collision_lookup.py` SHA：

`10c1d1339e742ca893fedb4aa51402addfba82e16e08f68339ea35d35ba3043b`

修复后结合 candidate v2：

* C：78 steps，goal=True，drivable=True，PASS
* D：75 steps，goal=True，drivable=True，PASS
* E：55 steps，goal=True，drivable=True，PASS

因此 **C/D/E blocker 已正式关闭**。

该修改是全局行为变化，最终提交之前还必须补 Dapai / Jiangtong / NTE200 相关回归。

# 19. A1 Route-End IDM Bug

A1 在 shadow runtime 中曾出现：

* 所有 target 均正确访问；
* route 基本正确；
* 车辆最终却停在 goal 前约 `4.8369 m`；
* goal=False。

最终根因并不是地图，也不是 goal polygon，而是 `AbstractIDMPlanner` 在“没有真实 leading object”时把 route endpoint 当成一个具有：

`length_rear = ego_length / 2 = 4.5 m`

的虚拟前车。

结合：

* virtual lead half length = 4.5 m
* IDM min_gap = 1 m
* rear axle → center = 2 m
* goal 距 route end = 3 m

理论提前误差约：

`4.5 + 1 + 2 - 3 = 4.5 m`

与实测 4.8369 m 高度一致。

最终把 free-road virtual endpoint 的：

`length_rear`

改成：

`0.0`

即将 route endpoint 正确解释为**零长度停止点，而不是一辆实体前车**。

当前 `abstract_idm_planner.py` SHA：

`0c64f7aeae858d6e456aeeabb867d72640382913f8ed090461eb40f49ea0b3a1`

A1 fixed shadow：

* trajectory states：252
* last step：251
* targets/order：TRUE
* goal reached：TRUE
* exception：None

因此：

**A1 goal / termination blocker = CLOSED。**

# 23. 地图验收原则

地图问题和 Planner / Engine 问题必须严格分层。

| 诊断结果                                       | 解释                                 | 正确动作                        |
| ------------------------------------------ | ---------------------------------- | --------------------------- |
| Standard CarFootprint bad > 0              | 真实 map gap                         | 根据真实轨迹做最小 additive patch    |
| Standard bad = 0，但 CollisionLookup bad > 0 | lookup false positive 候选           | 检查 CollisionLookup 几何/栅格    |
| shadow 忽略 mask 后仍停车                        | Planner / goal / occupancy blocker | 不继续补 mask                   |
| route endpoint 很远仍停车                       | leading-object / occupancy 优先      | 不继续改 endpoint               |
| 固定外推扫描不闭合                                  | 外推不可信                              | 获取真实 closed-loop trajectory |
| 多场景进程硬死                                    | 资源/生命周期问题                          | 一场景一 Python 进程              |

地图 patch 的真值必须来自**真实物理 CarFootprint**，而不是为了满足 CollisionLookup sampled occupancy 就不断把 bitmap 涂宽。

# 28. AI / 人机协作原则

* 提供事实；
* 执行代码；
* 产生真实日志；
* 验证 hash / Git / runtime；
* 保存版本。

**AI 说“应该可以”不算完成，AutoDL 实际运行结果和 Git diff 才是事实。**

修改已有核心文件时优先使用小 patch，而不是重写整个文件；一次只改一个明确问题。

# 31. Neural-MCTS 后续方向

→ PUCT

* state schema
* action order
* normalization
* value target
* root visit target
* scenario / episode split
* dataset manifest
* seed
* model config
* checkpoint metadata
* git commit

尤其不能把同一 episode 的相邻 frame 随机拆到 train 和 validation，这会造成严重时序泄漏。

当前更实际的研究方向是：在更多 benchmark 建立后研究 **adaptive MCTS budget / tree reuse / value guidance**，而不是立即训练大型网络。
